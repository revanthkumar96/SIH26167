# Fine-tuning

The problem statement lists *"a generic LLM/VLM with no remote-sensing
fine-tuning or domain adaptation"* under **Constraints and disqualifiers**.
Adaptation is not an enhancement here. Without it the submission is invalid.

Target: `Qwen/Qwen3-VL-2B-Instruct`, LoRA, two stages, on AWS.

---

## Feasibility is settled

Qwen3-VL 2B trains under **plain `transformers` + `peft`**. No LLaMA-Factory, no
ms-swift. This is confirmed from a published third-party adapter that trained on
a **Tesla T4** — sm75, 14.56 GiB, fp16 only. An A10G is roomy by comparison.

Known-good pins (`SOURCES.md` records where these came from):

```
transformers==4.57.1   peft==0.17.1
accelerate==1.7.0      qwen-vl-utils==0.0.14
torch 2.10.0+cu128
base revision 89644892e4d85e24eaac8bacfd4f463576704203
```

Pin the base revision. A silent upstream reweight mid-programme would invalidate
every number we have measured.

## Two stages

### Stage A — domain and cross-modal adaptation

**Data:** BigEarthNet.txt, cleaned and stratified per `DATA.md`.

Teaches SAR vocabulary, backscatter intuition, and joint optical+SAR reasoning.
This is the stage that literally discharges mandatory scope item 1, using the
dataset the problem statement names.

### Stage B — instruction tuning on the task mixture

**Data:** VRSBench + RSVQA + CDVQA train splits, plus the programme-C Indian
records.

Teaches the **output formats the metrics reward**: terse answers for exact-match
VQA, `[x1, y1, x2, y2]` for grounding, one or two sentences for captioning.

Stage B is worth more raw points than Stage A. A model that knows the right
answer but phrases it wrongly scores zero under exact match, and three of the
five scored criteria are exact-match or n-gram based. It also supplies the only
bi-temporal signal in the programme — BigEarthNet is single-date, so no amount of
Stage A produces change capability.

## Configuration

| knob | value | reasoning |
| --- | --- | --- |
| LoRA rank / alpha | **32 / 64** | headroom for a genuine domain shift |
| dropout | 0.05 | conventional |
| target modules | `q,k,v,o,gate,up,down` **+ the vision–language projector** | see below |
| vision encoder | frozen | full ViT tuning needs far more data and invites forgetting |
| learning rate | **1e-4**, cosine, 3% warmup | see below |
| precision | **bf16** | A10G is Ampere; no GradScaler, unlike the T4 path |
| effective batch | 64–128 via gradient accumulation | |
| epochs | 1–2 | VLM instruction tuning overfits fast |
| `max_pixels` | tuned up from the T4 default | the primary OOM lever |
| seed | fixed and recorded | |

### Two choices that are deliberate corrections

**Include the vision–language projector in `target_modules`.** The published
competitor adapter targets only `q,k,v,o,gate,up,down` — the language model. So
only language adapted, and the *visual* domain shift (SAR backscatter appearance,
multispectral false colour) was never learned at all. The projector is where that
shift actually lands.

It also matters for compliance. The problem statement asks for a *visual or
vision-language* component to be adapted. LLM-only LoRA is the weakest defensible
reading of that. Adapting the projector — and training the CNN in `CNN.md` —
gives an unambiguous answer.

**Learning rate 1e-4, not 1e-5.** The competitor adapter used 1e-5 with ~375
optimiser steps. That is roughly an order of magnitude below the conventional
LoRA range, and the adapter will barely have moved. This is the cheapest single
correction available to us.

### Vision tokens

The T4 run capped `max_pixels` at 200,704 — about **256 vision tokens**. That is
thin for grounding, and its reported mIoU of 0.362 is consistent with being
resolution-starved. Survivable on 120×120 BigEarthNet patches; badly insufficient
for sub-metre Cartosat. Raise it on the 24 GB card and treat it as the throughput
and memory dial.

## Train/serve parity — the thing that silently ruins fine-tunes

Three channels must match between training and inference. Any mismatch degrades
scores in ways that look like model weakness.

**1. Image normalisation.** Training rendering delegates to the serving path's
`stretch_to_uint8`. One implementation, imported by both.

**2. Prompt format.** Training prompts are rewritten into the exact convention
the tools use at inference — 0–1000 boxes, no `<ref>` markup.

**3. The evidence preamble.** The largest risk, covered in full in `DATA.md`.
At inference the model is handed measurements before its task prompt. If it never
saw that during training, it either ignores them or fights them. Roughly 40–50%
of training records must carry a preamble generated by the *same*
`format_evidence()` the controller calls, mixing decisive and orthogonal cases
and never a contradictory one.

Add a test asserting the training preamble matches `format_evidence()` output
byte-for-byte. Drift should fail at commit time.

## Measuring whether it worked

Baseline first, always: run the stock model through the harness on the prescribed
splits **before** training anything (`BENCHMARKING.md`). Without a before column
there is no evidence adaptation helped, and "we fine-tuned it" is an unverifiable
claim.

Base and adapted then appear as two rows of the same matrix — same harness, same
prompts, same splits, same seed. **That comparison is the single most important
artefact of the project.** It is what converts "we used an off-the-shelf model"
into "we adapted a model and here is the measured delta".

Watch for:

- **Regression on any task.** Stage B can help grounding while hurting
  captioning. If so, split into per-task adapters — `VLMTool` already names an
  `adapter` per instance, so the controller needs no change.
- **Format collapse.** Terse-answer training can bleed into captioning. Check
  caption length distribution, not just CIDEr.
- **Geographic hallucination.** Prompt the adapted model on an Indian scene and
  check it does not volunteer a European country. If it does, the cleaning in
  `DATA.md` leaked and the fix is upstream in preparation.

## What we are not doing, and why

**Full vision-encoder fine-tuning.** Needs far more data than we have, risks
catastrophic forgetting of general visual competence, and would not fit the
budget. LoRA on the projector captures most of the available gain.

**Training from scratch.** No.

**A larger base model.** Qwen3-VL 4B or 8B would likely score better, but 8B
does not fit the demo hardware and the serving story matters as much as the
benchmark. 2B keeps one model consistent from laptop fallback to AWS.

**Building on the competitor's published adapter.** It is Apache-2.0 and we
could. We do not: it is theirs, it is narrow, and the comparison we need is
against a clean baseline we produced ourselves.
